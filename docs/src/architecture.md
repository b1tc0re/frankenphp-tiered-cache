# Архитектура

```text
PHP / FrankenPHP workers
          ↓
      TieredCache
       ┌────┴────┐
       ↓         ↓
  MemoryCache   RedisCache
    локальный   общий источник
       L1          истины
```

`MemoryCache` принадлежит одному Go-процессу. Redis хранит авторитетные данные и
объединяет экземпляры FrankenPHP.

## Чтение и запись

- `Get` сначала проверяет L1. При промахе читает Redis и записывает найденное
  значение в L1 с оставшимся TTL.
- Записывающие операции сначала завершают изменение в Redis, затем обновляют или
  сбрасывают локальный L1 и отправляют invalidation другим экземплярам.
- `Increment` и `Decrement` изменяют счётчик атомарно в Redis и удаляют его копию
  из L1.
- `Flush` очищает Redis и L1, затем отправляет событие полного сброса.

Успешное изменение Redis считается committed. Если после него не удалось
обновить L1 или отправить событие, значение в Redis не откатывается. Экземпляр
переходит в `degraded`, сохраняет недоставленную invalidation и повторяет её во
время recovery.

## TTL

TTL задаётся как положительное относительное время. Для хранения без срока есть
отдельная операция `Forever`. `TieredCache` передаёт в L1 оставшееся время жизни,
а не полный исходный TTL.

`MemoryCache` проверяет срок по монотонной части `time.Time`, которая существует
только в текущем процессе. Она не сериализуется и не сравнивается между pod'ами.
Просроченная запись считается отсутствующей сразу при достижении срока, даже
если фоновая уборка ещё не удалила её физически.

## Invalidation между экземплярами

Обычные изменения распространяются через Redis Pub/Sub. Потерянные во время
разрыва соединения сообщения не восстанавливаются транспортом, поэтому при
ошибке подписки экземпляр очищает L1 и остаётся `degraded` до успешного
переподключения.

Для очисток Redis в обход FrankenPHP используется `CLIENT TRACKING` по одному
общему marker key на DB и префикс. Удаление или изменение маркера, очистка всех
ключей префикса, а также `FLUSHDB`/`FLUSHALL` очищают L1 у подписанных экземпляров.
Маркер создаётся через `SETNX`, поэтому рестарты используют ту же запись.

Для этой функции нужны Redis 6.0+, RESP3 и ACL-права для tracking-команд и
служебного ключа. Все экземпляры должны использовать одинаковые Redis endpoint,
DB и `KeyPrefix`. Внешнее изменение отдельного cache key, при котором маркер
остаётся нетронутым, не вызывает сброс L1. Настройки и требования описаны в
[конфигурации](configuration.md).

L2-изменение и Pub/Sub-публикация — две отдельные команды. Если процесс завершится
между ними, другой экземпляр может временно вернуть старое значение из L1 до
истечения его TTL или следующего сброса локального кеша.
